# Plan #11 — an installer executable: one idempotent .py that installs, recovers and cleans

## Definition of done
*Proposed* (the plan-`Y` below accepts it; `intent-reading: off`). The operator's words, quoted from
`provenance/11.md` entry 1:

> we need an installer "executable" (.py) that is a full running automaton that will understand the current
> installation steps and recover and clean.  it also needs to be idempotent.  in the world of windows, it was
> the "installer.exe" or "setup.exe"

and entry 2, which moved the build:

> i prefer the channels path so give me a hand-carry for the installer and i'll have the `pltrinh1122/dyad-system`
> (ptolemy) build it and propose it through the channels for you to review and merge.

Proposed completion:

> The reference carries an installer executable — one `.py` a stranger fetches from a core Release and runs on an
> empty machine — that performs the install steps `install.sh` performs today, **detects and repairs** a partial or
> broken install instead of refusing, **cleans** every artifact it created when asked, and is **idempotent**: a
> second run reports `0 changes`. It is built by `pltrinh1122/dyad-system` from this row's hand-carry, offered as a
> fork pull request plus its channel post, and admitted, reviewed, merged and released by this steward. This row
> delivers the hand-carry and the review; it writes no installer code.

## Intent as read
- **"automaton" is the operator's plain-English sense, not this system's term.** The vocabulary's automaton is
  "a non-inferring party that runs a released definition … it executes a `Y` the ledger already holds and decides
  nothing". An installer runs before any ledger exists, so it holds no `Y` and is not that. What the operator asks
  for is the gloss the same entry gives — *automatic, not autonomous*: one command, no second question, no human
  judgement in the middle. The hand-carry says that in those words, so no Rule is bent to fit the request.
- **"the current installation steps"** are the five of `dyad/scripts/install.sh` (186 lines), which
  `dyad/surface.md` names as the frozen surface item `installer`, with its flags, its two variables, the launcher,
  its marker and the seed prompt.
- **"recover" is the heart of it.** This system's own first boot stopped at the play-book's step 5 and left the
  install on branch `first-boot` with `main` at its root commit, because `land.fetch` takes the fetch path for an
  `origin` that exists and is empty. Nothing detected that; row #3 exists because of it, and so does the incident
  of 2026-11-20. An installer that recovers would have made both unnecessary.
- **"clean" exists today only as prose**: the undo lives in a comment in the script's header, so the operator
  executes it by hand or not at all.
- **The build is not this system's** (entry 2). This row's mutation is the hand-carry, then the intake, review and
  merge of what comes back.

## Falsification
Record: `agent-corpus/falsification/11-installer-hand-carry.md`, written with step 1's PR.

- **A1 — a specification with no form is a wish, not a brief.** Attack: the dyad has a `specs` craft for exactly
  this and the hand-carry ignores it. *Survives, scoped*: that craft is in the reference and is **not installed
  here**, so writing in a form this system does not carry would be inventing one. The hand-carry is a plain
  agent-zone document; if the review finds its shape wanting, installing `specs` is its own row.
- **A2 — ptolemy builds the wrong thing, because prose under-determines code.** *Survives, scoped*: the risk is
  real and the answer is that Appendix A's acceptance criteria are **commands with expected output**, not
  adjectives — two installs and a `0 changes`, six named broken states and the recovery each must reach, a clean
  that returns the host to its pre-install reading. A brief whose acceptance is executable can be wrong, but it
  cannot be vague.
- **A3 — the steward reviewing a change its own operator commissioned is not independent review.** *Confirmed, and
  stated*: the operator is the common party to both systems, so the independence this buys is not of interest but
  of **agent** — a second model, in another instance, with its own frame, building from a written brief instead of
  from this session's assumptions. That is exactly what was missing when D1, D3 and D4 were authored and reviewed
  by one agent today.
- **A4 — a `.py` installer cannot run before Python exists, and `install.sh` can.** *Refuted in part*: Python
  3.12+ is already the kernel pin (Rule-14 property 2) and `install.sh` already **refuses** without it, so no host
  can install today without it. What the shell bootstrap preserves is the quality of that refusal — a readable
  message rather than a kernel `exec` error — and step 4 keeps it for that reason.
- **A5 — recovery can leave a worse state than refusal.** *Survives, scoped*: the hand-carry requires
  read-then-report-then-act — the installer prints the state it found and what it will do, every step classed by
  `crafts/sysadmin/dmc/install-step-class.jsonld`, and no destructive step automatic. A recovery that cannot
  classify what it found must refuse and say so, which is the behaviour `dyad/dmc/install-refusal.jsonld` already
  governs.
- **A6 — the hand-carry names another of the operator's repositories in a tracked file.** *Refuted on checking*:
  both `The-Dyad-Practice-Commons/the-dyad-system-steward` and `pltrinh1122/dyad-system` are public, so the name
  discloses nothing. The constraint that a private repository's name never enters the channels repository is
  unaffected and still holds for the post.
- **A7 — concurrency** (Rule-16): no other session's presence file claims any file this plan touches. `program`
  holds no rows and its `files` set is empty; this unit holds the rest.

## Appendix A — the hand-carry, as step 1 will write it
See the reply that carries this plan: the document is reproduced there in full, and the plan-`Y` accepts it as the
text step 1 commits. Its sections are fixed: **What is wanted** (one `.py`, automatic, idempotent, recovering,
cleaning); **What exists today** (`install.sh`'s five steps, the frozen surface row, `dyad install`, the launcher

`crafts/sysadmin/dmc/install-step-class.jsonld`); **The six recovery cases** (no tree; tree without launcher;
launcher without marker; an `origin` that exists and is empty, the `land.fetch` fault that broke this system; an

(launcher, marker, `git config dyad.attention.clone`, a `.git` the installer created, the paths `dyad install`
printed, and the installer's own logs); **Idempotence** (`0 changes` on a second run, per
`crafts/syseng/rules/idempotence.md`); **Acceptance criteria** as commands with expected output; **The version
question** (minor beside, not major replacing — step 4); and **The route** (a fork PR of the reference plus a
channel `request` post carrying the operator's words, admitted and merged by this steward).
