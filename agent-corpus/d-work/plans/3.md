# Plan #3 — the home cannot persist as a background session

## Definition of done
*Proposed* (this row opens on the operator's `Y` below; the question names it, Rule-3 Scope):

> This system has a home the operator can attend: one committed ops script the operator runs in their
> own terminal, which starts the home with a tty so it persists past its first turn. The three start
> attempts of 2026-11-20 are in the change log with their outcomes, the incident is recorded, and the
> post that carries it upstream is drafted and handed to the operator.

## Intent as read
First boot delivered a home that ran one turn and exited (incident row, 2026-11-20). The intent is not to
re-run the same start: it is to give the home the one thing it lacks — a terminal — by the form Rule-18
prescribes for a command the operator runs on the agent's behalf, and to leave the cause recorded where
upstream reads it. The home's own configuration question is **not** in this row's scope: it is the home's
to ask and the operator's to answer, and this row only makes a home that can hear the answer.

## Mutation
`order: required`.

- **step H1 — the ops script** `workstation-corpus/ops/3-h1-start-home.sh`, in the sysadmin craft's
  ops-script form (`crafts/sysadmin/rules/ops-scripts.md`): class reversible, undo one command,
  `postcondition()` reading `ps` for a live `claude … --remote-control program`, `# destructive: none`.
  Its body execs `<git common dir>/dyad-launch-home` from this checkout. The operator runs it once in a
  terminal; the agent never runs it (Rule-18 Conduct: never an inline block, and the script's exit code
  is completion evidence).
- **step H2 — the change log** (`workstation-corpus/CHANGELOG.md`): four rows under #3 — the three
  start attempts already made (the first started and exited; the launcher's `--resume` refused for want of
  a session id; the explicit `--resume <id>` refused for want of a prompt) and H1's own run, its outcome
  the pasted exit code and the postcondition's output. Rule-8 keeps the row of a reversible action however
  it ended, so a failed attempt is a row with a failure in `outcome`.
- **step H3 — the incident and the upstream post** (agent zone): the incident row already drafted in
  `agent-corpus/audits/INCIDENTS.md`, plus `agent-corpus/channels-drafts/home-exits-after-one-turn.md`, an
  `issue` post in the channels format naming what was observed, where
  (`dyad/runbooks/first-boot.md` `home-start`, `dyad-operator` 1.6.0, tree sha256 `e711ade9…` matching its
  registry row, so the tree is unmodified and the fault is upstream's) and the mechanism: a `nohup`/`setsid`
  `claude` has no tty, so the CLI takes its `--print` path, and the step's postcondition cannot tell a home
  that persists from one alive for a single turn. This system has no channels membership, so the post is
  handed to the operator, not posted (Rule-3 Incidents).

**PRs**, one zone each (Rule-1): a **workstation-zone** PR for H1 and H2, an **agent-zone** PR for H3. No
accreted row; this plan states no mandate scope, so it carries none. Host actions: H1's run is the
operator's, class reversible, undo `pkill -f 'claude .*--remote-control program'`; the agent runs no host
action in this row.

## Falsification
- **Attack: the right fix is to correct `home-start`'s postcondition, not to add an ops script.** Survives,
  scoped: the postcondition is core-craft text in an unmodified tree, so correcting it here would modify a
  craft this system installed as it came (Rule-11 property 2) and would be overwritten by the next install.
  H3 carries it upstream instead. The ops script is this system's own remedy, which is what an instance owes
  itself.
- **Attack: an ops script is unnecessary — the operator can type the launcher's path.** Refuted by Rule-18:
  a command the operator runs for the agent is a committed, syntax-checked file or it is not asked, and its
  text and outcome are provenance. The typed form leaves nothing to compare the pasted output against.
- **Attack: H1 only moves the problem — a tty-less start is the real design, so the home should be a cloud
  session instead.** Survives: the play-book's own E2-cloud branch says as much, and a cloud home may well
  be the better shape here. That is a different row with a different definition of done; this one gives the
  operator an attendable home today on the host they are on, and names the alternative rather than hiding it.
- **Attack: #1's done-`Y` was given on a false claim, so #1 should reopen.** Refuted — the home was running
  when its Done was asked and verified, and Rule-16 never reopens a `done` row; a new row refs it, which is
  this one.
- **Presence overlap** (Rule-16): `program`'s presence file shows `[SAME ROOT AS YOU]` — it ran in this
  working tree. Its `files` set is empty, so no plan-file overlap; the root collision is why the home's own
  first reply reported writing no board entry, and a worktree for the home is the follow-on this plan names
  in its counter, not a step it takes.
